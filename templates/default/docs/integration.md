# 将来の連携と部署間の利用

現在は単一のNext.jsアプリとPostgreSQLで共有マスタを利用する。部署ごとの機能を小さく追加し、同じ人物・部署の内部IDを参照できる構成にする。

## 利用シナリオ

人事担当がユーザー・部署を管理し、総務担当が備品を管理する。今後、教育担当の研修機能を加える場合も同じUser / Departmentを参照する。備品の担当者と研修の受講者はUser.id、組織の境界はorganizationIdで表す。

現在のAdmin / Manager / Userは役割の基盤で、人事・総務・教育ごとのPermission割当や部署単位スコープを表すものではない。部門別の権限要件が出たら[認可仕様](authorization.md)を拡張し、既存の範囲を暗黙に変えない。

## 境界と入口

Domainごとに入力・データアクセス・serviceを分ける。将来、外部APIから同じ業務操作を使うときは、認証済み操作者と組織を確定して既存serviceを呼ぶ。画面のServer ActionはHTTP入口の一つで、業務service自体を画面に依存させない。

API追加時には認証・認可・入力Schema・バージョン・エラー応答・監査・再試行時の重複対策を設計する。別DBへ分離する場合はマスタの管理主体、ID対応、同期方法、障害時の扱いも別途決める。現在、別システム間の同期や外部APIが実装済みとは扱わない。

CSV / Excel / JSON / APIを将来追加する際にも、内部IDとコード・名前を分離しておく。現在の[CSV](csv.md)は形式の読込検証・医療台帳の出力と確認付き新規一括登録までで、既存台帳の更新・xlsx、マイクロサービス、Message Broker、Event Busは提供しない。使用しないIntegration Frameworkを先行追加しない。

## 設計を確認する例

社員研修を追加するときは、研修DomainがOrganizationとUserを参照し、受講日・期限・状態を自分のモデルで管理する。Equipment repositoryを呼んだり、備品のテーブルへ研修属性を足したりする必要はない。

共有マスタの一貫性・Permission・監査・UIから分離したserviceを保ったまま新Domainを追加できるかをレビューする。この文書は連携の設計方針で、研修機能を自動実装する指示ではない。AIによる実際の新機能追加は、別途用意する生成プロジェクトで検証する。
