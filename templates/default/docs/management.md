# 共通画面・ユーザー／部署管理

/dashboardにヘッダー・サイドバーを配置する。Adminはユーザーと部署を登録・編集でき、Managerは一覧参照のみ、Userはダッシュボードのみ。メニュー非表示に加え、各ページとServer Actionで権限を検査する。権限のないページはデータを取得せず案内を表示する（HTTP 403応答ではない）。

## 操作

- ユーザー: 氏名・メール・社員番号・所属・ロール・有効状態を登録／編集する。新規登録の初期パスワードは12〜128文字。標準Better Auth credential Accountへハッシュ保存し、ログ・監査・レスポンスへ返さない。初期パスワードの通知や変更強制・リセットは未実装。安全な経路で本人へ伝える。
- ユーザーを物理削除する画面は作らず、無効化を使う。再有効化も可能。メール・ロール・有効状態の変更ではセッションを削除する。メール変更はemailVerifiedをfalseへ戻す。
- 自分自身の無効化・ロール変更は拒否する。有効なAdminを1名以上残す判定をSerializable transaction内で行う。
- 部署: コード・名称・親部署を登録／編集する。自己参照・子孫への移動・組織をまたぐ親部署を拒否する。ユーザーや子部署のある部署は削除できない。削除前にチェックボックスで確認する。

一覧は組織内の全件を安定した順序で表示する。大規模組織向けのページング・検索は未実装。親部署の選択肢は自部署を除外するが、子孫の選択も保存時にサーバーで拒否する。

## 入力と更新

management/validation.tsにFormData検証を集約する。UUID・文字数・必須・メール・ロール・状態・パスワードをサーバーで確認し、クライアントのrequired等は補助とする。組織IDと操作者IDはセッションから取得し、フォームから受け取らない。

管理サービスは最新の権限をトランザクション内で確認し、業務更新・Account生成／Session削除・監査記録を一括確定する。メール・社員番号・部署コードの重複や競合は日本語で案内し、DBの生エラーや秘密を表示しない。P2034は画面再読込・再操作を案内する。監査Userスナップショットは従来の許可属性だけなので、氏名・メールの変更値は記録しない。

Server ActionsはNext.jsのOrigin検査に加え、BETTER_AUTH_URLとOriginの一致を要求する。アクセスするURLと設定を一致させる。プロキシ運用の前提はauthentication.mdを参照。

## 画面と検証

オレンジを主要操作に使い、PCはサイドバー、狭い画面は横並びメニューへ切り替える。入力ラベル、キーボード操作、フォーカス表示、本文へのスキップリンク、送信中の無効化、エラー案内を提供する。@kumuno/adminをvendorの未公開tgzから導入する。

npm run checkでlint・型・単体・基本ブラウザー検証、test:template:dbで生成物の実DBとブラウザーの部署／ユーザー登録・編集・無効化／再有効化・部署削除・参照ロール制限を確認する。実運用DBのMigrationや初期管理者プロビジョニングは自動実行しない。

## 共通パッケージ

ユーザー・部署の入力欄は@kumuno/adminのUserFields / DepartmentFields、送信フォームは@kumuno/admin/formのManagementFormを利用する。rootはサーバーで描画でき、/formはReact 19のuse client境界を保つ。Reactはpeer dependency。Prisma・Next.jsへの依存はない。

アプリは組織内のデータ取得・参照/編集可否・Server Action・Validation・最新の操作者・保存と監査を所有する。公開する入力値にAccountやセッションを含めない。パッケージにDBや認証を自動接続する機能はなく、既存の権限規則を維持する。

CSSは既存のform-grid / management-form / primary-button / notice-error / notice-successを利用する。独自権限編集UI、汎用マスタCRUDは未実装。
